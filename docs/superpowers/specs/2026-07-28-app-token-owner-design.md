# Явный владелец app-токена портала (`b24_apps.user_id`)

Дата: 2026-07-28
Пакет: `x3group-dev/bitrix24-api-laravel`
Целевая версия: **3.4.0**

## Задача

Сделать владение app-токеном портала явным и разрешить запись в `b24_apps` только двум
источникам:

1. установка или переустановка приложения;
2. обновление токена в `b24_users`, когда пользователь совпадает с установщиком.

## Почему

Сейчас в `b24_apps` нет ID пользователя, которому принадлежит токен. Владение неявное —
оно закодировано только внутри самой строки токена. Из-за этого любая запись «вслепую»
молча меняет владельца, и обнаружить это можно лишь декодированием токена.

Именно так возник инцидент look.bitrix24.ru (2026-07-27): токен рядового сотрудника
оказался в `b24_apps`, админ-методы (`userfieldconfig.*`) начали падать «нет прав», у
клиента пропали настройки полей, а переустановка администратором держалась 32 минуты —
до первого действия любого сотрудника. Тот же баг независимо поймали в `project-dashboard`
в тот же день («токен Марины оказывался в строке Евгения»).

Корневая причина утечки через глобальную шину событий уже устранена в **3.3.1**
(`EventDispatcherAdapter` держит слушателей в приватной шине экземпляра). Эта спека
закрывает вторую половину проблемы: делает владельца явным, чтобы запись в `b24_apps`
была решением по правилу, а не побочным эффектом.

Аудит на 2026-07-28 показал, что повреждённые порталы есть и сейчас: `look` в
dependent-fields, `shadt.bitrix24.ru` и `helptime.bitrix24.ru` в `hh` (2 из ~290).

## Данные

В `b24_apps` добавляется колонка:

- `user_id` — `unsignedInteger`, **nullable**, с индексом.

NULL означает «владелец не установлен или не доверен». Правило 2 для такой строки не
срабатывает — поведение fail-closed.

`user_id` записывается только при установке. Обновление токена владельца его не меняет.

### Бэкофилл

Миграция проходит по всем строкам `b24_apps`:

1. декодирует владельца из `access_token`: `hexdec(substr($token, 24, 8))` — в токене
   Bitrix эти 8 hex-цифр содержат ID пользователя (проверено на 90 пользователях одного
   портала: 90 совпадений, 0 промахов; при рефреше владелец сохраняется);
2. ищет его в `b24_users` по `(member_id, user_id)`;
3. записывает `user_id`, **только если найденный пользователь `is_admin`**; иначе
   оставляет NULL.

Это не даёт узаконить уже подменённого владельца: на повреждённых порталах в токене лежит
не-админ, такие строки остаются с NULL и попадают в отчёт.

Миграция печатает сводку: сколько строк заполнено, сколько осталось NULL и по каким
порталам. Список NULL — готовый вход для команды ремонта.

Токены короче 32 символов и пустые считаются нераспознанными: NULL.

## Политика — `AppTokenWriter`

Единственный владелец правил. Решения — чистые функции:

```php
// правило 1 — существующее поведение, без изменений
public static function shouldWrite(bool $appExists, bool $isAdmin): bool
{
    return !$appExists || $isAdmin;
}

// правило 2 — новое
public static function shouldPropagateFromUser(?int $installerUserId, int $userId): bool
{
    return $installerUserId !== null && $installerUserId === $userId;
}
```

Исполнители:

- `saveIfAllowed(LocalAppAuth $auth, string $memberId, bool $isAdmin, ?int $userId = null)` —
  четвёртый аргумент **необязательный**, чтобы не ломать сигнатуру публичного метода в
  минорной версии. При разрешённой записи сохраняет `user_id` установщика; если аргумент
  не передан, колонка не изменяется;
- `propagateFromUser(string $memberId, int $userId, AuthToken $token)` — если
  `shouldPropagateFromUser()` разрешает, обновляет в `b24_apps` поля `access_token`,
  `refresh_token`, `expires`, `expires_in` и сбрасывает `error_update` в 0. `user_id`,
  `domain`, `application_token`, `oauth_server_url` не трогает. Если строки `b24_apps` для
  этого `member_id` нет — не делает ничего (нормальная ситуация: приложение ещё не
  установлено).

Обе операции пишут в лог факт записи (member_id, user_id, причина) — как уже делает
`saveIfAllowed`.

## Точки записи

Ровно три, все вызывают `AppTokenWriter`.

1. **`InstallService::handleInstallPage()`** — правило 1. Метод уже вычисляет
   `$userId = $profile->ID`; он передаётся в `saveIfAllowed()`.

   **Владельцем портала может стать только администратор.** Метод уже получает профиль
   устанавливающего (`getCurrentUserProfile()`), и если `ADMIN` не выставлен — установка
   прерывается ошибкой, а не проходит молча. Это ужесточает правило 1: раньше
   `shouldWrite(appExists: false, isAdmin: false)` разрешал первую установку кем угодно,
   и не-админ мог стать записанным владельцем — то есть ровно тем состоянием, которое
   бэкофилл намеренно отказывается создавать. Ошибку ловят тонкие стабы-контроллеры
   приложения и показывают пользователю понятное сообщение.

   Здесь же устраняется остаточная дыра: probe-клиент строится из placement-запроса и
   несёт токен **открывающего**, а `getCurrentUserProfile()` делает REST-вызов. Сейчас
   этому клиенту передаётся `resolve('appEvents')` — диспетчер со слушателем записи в
   `b24_apps`; изоляция 3.3.1 тут не помогает, потому что слушатель и клиент — один
   экземпляр. Заменяется на свежий `new EventDispatcherAdapter` без слушателей.

2. **`UserAuthDatabaseStorage::saveRenewedToken()`** — правило 2, путь «токен протух и
   обновился». После записи в `b24_users` вызывает `propagateFromUser()`.

3. **`B24AppUserMiddleware`** — правило 2, путь «установщик открыл приложение». После
   записи/обновления строки `b24_users` собирает `AuthToken` из полей запроса
   (`AUTH_ID`, `REFRESH_ID`, `AUTH_EXPIRES`) — теми же значениями, что только что легли в
   `b24_users`, — и передаёт в `propagateFromUser()`.

`AppAuthDatabaseStorage::saveRenewedToken()` не меняется: после 3.3.1 туда попадает только
рефреш самого app-клиента, а он владельца не меняет.

Копирование пользовательского placement-токена в `b24_apps` безопасно: установка уже
делает ровно это — `InstallService` берёт `$request->input('AUTH_ID')` из placement-запроса
и сохраняет его как app-токен. Тот же тип токена, тот же владелец.

## Команда ремонта

`php artisan bitrix24:reanchor-app-token`

Находит строки `b24_apps`, где `user_id IS NULL` либо владелец не является админом по
`b24_users`. Для каждой:

1. выбирает свежайшего админа портала (`is_admin = true`, `ORDER BY expires DESC`) или
   указанного через `--user`;
2. записывает его токены и `user_id`;
3. проверяет живым вызовом `user.admin`;
4. если вызов вернул `false` или упал — **откатывает строку** к прежним значениям.

Порталы без единого админа в `b24_users` помечаются как «нужна переустановка» и не
изменяются.

Флаги: `--dry-run`, `--member=`, `--limit=`, `--user=`.

Вывод — таблица: портал, текущий владелец, предлагаемый владелец, результат проверки.

## Тестирование

В `require-dev` добавляется `orchestra/testbench`. Сейчас тесты пакета чисто юнитовые, без
контейнера и БД, поэтому сами записи в таблицы не покрыты — именно так этот класс багов и
прожил: `AppTokenWriter::shouldWrite` был протестирован, а то, что запись идёт мимо него
через шину событий, не проверял никто.

**Юнит:** `shouldPropagateFromUser` — NULL-владелец, совпадение, несовпадение.

**Feature:**

- рефреш токена установщика → `b24_apps` обновился;
- рефреш токена постороннего пользователя → `b24_apps` не тронут;
- вход установщика через middleware → `b24_apps` обновился;
- вход постороннего через middleware → `b24_apps` не тронут;
- `user_id IS NULL` → правило 2 не срабатывает ни на одном пути;
- установка записывает `user_id`;
- probe-клиент в `handleInstallPage()` не пишет в `b24_apps` при рефреше своего токена.

**Миграция:** владелец-админ → `user_id` заполнен; владелец не админ → NULL; нераспознанный
токен → NULL.

**Команда:** `--dry-run` не пишет; боевой прогон перепривязывает; при неуспешной проверке
`user.admin` строка откатывается; портал без админов пропускается.

## Совместимость и выкатка

Версия **3.4.0**: колонка nullable, изменения аддитивные, обратной несовместимости в API нет.

Порядок:

1. релиз 3.4.0;
2. в каждом приложении бамп версии и `php artisan migrate`;
3. `bitrix24:reanchor-app-token --dry-run` — посмотреть список;
4. боевой прогон ремонта.

Для `hh` это чинит `shadt.bitrix24.ru` и `helptime.bitrix24.ru`, для dependent-fields —
`look.bitrix24.ru`.

Получат после бампа: `dependent-fields`, `hh`, `tasks`, `yclients`, `base`,
`project-dashboard`. Не получат до апгрейда мажора: `project-meeting-summary` (2.0.7),
`export2googlesheet` и `list2googlesheet` (1.x-dev).

## Вне рамок

- Перевод `dependent-fields` с рукописного `InstallController` на `InstallService` —
  отдельный MR после релиза 3.4.0, чтобы не смешивать изменение пакета с рефакторингом
  приложения.
- Ужесточение `shouldWrite` до проверки `ONAPPINSTALL` — не нужно: замер показал, что
  `/install` дёргается только при установке и переустановке (за сутки на 115 порталах и
  104 712 вызовах API — 2 портала, 9 обращений), поэтому текущего условия достаточно.
- Снятие локального `IsolatedEventDispatcher` в `project-dashboard` — после бампа, отдельно.
