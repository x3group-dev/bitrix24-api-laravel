# Консольные команды

Пакет регистрирует три artisan-команды; отдельно подключать их не нужно — они появляются в
`php artisan list` сразу после установки. Ни одна из них не ставится пакетом в планировщик:
периодичность выбирает приложение (в `routes/console.php` либо в своём `Kernel`). Обязательная
запись в crontab — только `schedule:run` для автообновления токенов, см. `README.md`.

Модель владения app-токеном (`b24_apps.user_id`) и два правила записи описаны в `README.md`,
раздел «Владелец app-токена портала»; здесь — только команды.

| команда | зачем |
| --- | --- |
| [`bitrix24:backfill-app-owner`](#bitrix24backfill-app-owner) | проставить владельца порталам, установленным до появления колонки |
| [`bitrix24:reanchor-app-token`](#bitrix24reanchor-app-token) | починить порталы, чей app-токен принадлежит не администратору |
| [`bitrix24:remove-uninstalled`](#bitrix24remove-uninstalled) | удалить токены порталов, которые уже не оживут |

Первые две — пара: бэкофилл только **записывает уже сложившееся** владение и заодно показывает,
какие порталы сломаны, а чинит их ремонт. Порядок выката при обновлении с версии ниже 3.4.0
(`migrate` → бэкофилл → ремонт) — в `README.md`.

## `bitrix24:backfill-app-owner`

```bash
php artisan bitrix24:backfill-app-owner --dry-run
php artisan bitrix24:backfill-app-owner
```

Проставляет `b24_apps.user_id` порталам, установленным до появления этой колонки. Владелец
декодируется из самого `access_token` и принимается, **только если это подтверждённый по
`b24_users` администратор того же портала**; любое сомнение оставляет `NULL` (fail-closed). На
повреждённом портале в токене лежит рядовой сотрудник, и записать его владельцем значило бы
узаконить подмену.

Команда ничего не чинит и не делает ни одного REST-вызова: она только фиксирует, кому токен
принадлежит уже сейчас.

**Когда запускать.** Первый раз — сразу после `php artisan migrate` при обновлении. Дальше —
**повторные прогоны и есть нормальный режим**: обрабатываются только строки с `user_id IS NULL`,
поэтому запуск идемпотентен и дозаполняет то, про что знание о правах появилось позже
(`b24_users.is_admin` пишется, когда пользователь заходит во фронтенд приложения). Ни
проставленное ранее, ни назначенное вручную ремонтом прогон не пересматривает.

**Сводка** делит порталы на четыре корзины:

| корзина | что это значит | что делать |
| --- | --- | --- |
| **заполнено** | владелец разобран и подтверждён админом | ничего |
| **владелец не админ** | это и есть искомая поломка | порталы перечисляются поимённо и идут в `bitrix24:reanchor-app-token` |
| **владелец неизвестен** | владелец разобран, но строки о нём в `b24_users` нет — прав мы не знаем | ничего; для приложений на API-роутах это норма |
| **токен не разобран** | владельца не удалось вытащить из `access_token` | единичные случаи нормальны; массовые означают ошибку интеграции (не та колонка, сменился формат токена, значения зашифрованы) — разбирайтесь с ней, а не с порталами поштучно |

Опции:

- `--dry-run` — посчитать и показать сводку, не записывая ничего. Заполнение при этом
  прогоняется **по-настоящему**, но в заведомо откатываемой транзакции: цифры считает ровно тот
  код, который потом и будет писать, поэтому они точные, а не оценочные.

Код возврата всегда нулевой: непустые корзины — это диагноз, а не сбой прогона.

## `bitrix24:reanchor-app-token`

```bash
php artisan bitrix24:reanchor-app-token --dry-run
php artisan bitrix24:reanchor-app-token
```

Ремонт порталов, у которых app-токен принадлежит не администратору: команда подбирает
администратора портала по `b24_users` (самого свежего по `expires`) и перепривязывает портал на
него.

**Пишет токен, а не только колонку.** Смена одного `user_id` ничего не чинит: правило 2 донесло
бы токен нового владельца до `b24_apps` лишь тогда, когда тот сам откроет приложение, — а админ,
во фронтенд не заходящий, не сделает этого никогда. Поэтому переносится токен целиком
(`access_token`, `refresh_token`, `expires`, `expires_in`) вместе с `user_id`, и обнуляется
`error_update`: при `error_update >= 10` портал исключён из ротации обновления токенов.

**Результат проверяется живым вызовом `user.admin`** тем самым токеном, который только что
записан. Исходов три:

- **перепривязан** — проверка сказала «админ»;
- **откат** — строка возвращена в прежний вид целиком;
- **откат отменён** — строку успел переписать кто-то ещё (живая проверка идёт через диспетчер
  событий, чей слушатель сохраняет обновлённый токен прямо в `b24_apps`), поэтому токен
  оставляется свежий, а прежний владелец возвращается: закреплять за порталом исходную аварию
  нельзя.

Прогон, в котором не выжила **ни одна** перепривязка (были откаты и ни одного успеха), возвращает
ненулевой код.

**Корзины.** Порталы раскладываются по пяти:

| корзина | что это значит | что делать |
| --- | --- | --- |
| **здоров** | владелец подтверждён админом в `b24_users` | ничего |
| **на ремонт** | владельца нет либо он точно не админ, и на портале есть админ со свежим токеном | команда чинит сама; только эта корзина расходует `--limit` |
| **ждёт входа админа** | админы есть, но у всех токен старше `--max-age` | пусть любой администратор один раз откроет приложение — следующий прогон починит |
| **нужна переустановка** | владелец точно не админ, перепривязаться не на кого | переустановка приложения администратором |
| **нет данных** | свидетельств о правах нет: владелец записан, но строки о нём в `b24_users` нет, либо `user_id IS NULL` и админов на портале нет | ничего; **это не «нужна переустановка»** |

`b24_users.is_admin` заполняет только `B24AppUserMiddleware`, то есть заход пользователя на
фронтенд. У приложения на одной API-группе роутов (`routes/b24app.php`) `b24_users` пуст, и в
корзину «нет данных» закономерно попадает весь флот — звать клиентов на переустановку тут не за
что.

Опции:

- `--dry-run` — показать план, не записывая ничего.
- `--member=` — обработать только этот `member_id`.
- `--user=` — взять токен именно этого пользователя (обязан быть админом); **действует только на
  корзину ремонта** — диагностические корзины команда не трогает вовсе. Если такого пользователя
  на портале нет, портал попадает в «без кандидата»; если он есть, но не админ, — в «отказано»
  (это разные ответы намеренно).
- `--limit=200` — максимум **ремонтируемых** порталов за прогон, `0` — без ограничения. Счётчики в
  сводке всегда полные, за весь флот; обрезаются только строки таблицы, и о числе скрытых строк
  команда сообщает отдельно.
- `--max-age=30` — не брать во владельцы админа, чей токен не обновлялся дольше стольких дней
  (`0` — без ограничения). Защищает от замены живого токена не-админа на мёртвый токен админа. При
  `--max-age=0` корзина «ждёт входа админа» пуста по определению.
- `--skip-verify` — не проверять результат вызовом `user.admin`. **Разрешён только вместе с
  `--member`:** без живой проверки прогон способен разложить по флоту мёртвые токены, а отменить
  это нечем. Одиночный `--skip-verify` команда отвергает с ненулевым кодом, ничего не сделав.

В лог пишутся `info` `reanchored app token` на каждую перепривязку и `warning` `reanchor rolled
back` / `reanchor rollback skipped: row changed under us, ownership restored` на неудачные.

## `bitrix24:remove-uninstalled`

```bash
php artisan bitrix24:remove-uninstalled --dry-run
php artisan bitrix24:remove-uninstalled
```

Удаляет токены порталов, которые уже не оживут: с которых приложение удалено (OAuth
`NOT_INSTALLED`) и у которых подписка кончилась больше `--expired-days` назад (OAuth
`PAYMENT_REQUIRED`). Сетевые ошибки и таймауты не трогает — такие порталы могут ожить. Вместе со
строкой `b24_apps` удаляются и строки `b24_users` этого портала.

**Зачем она нужна отдельно.** Штатное обновление токенов (`renewTokens()`) удаляет `NOT_INSTALLED`
само, но только пока `error_update < 10`; портал, на котором обновление упало десять раз, из
ротации исключён и остаётся в БД навсегда. Здесь фильтра по `error_update` нет.

**Когда запускать.** Периодически — типично раз в сутки через планировщик приложения — либо
разово, когда флот распух от мёртвых порталов. Прогон небыстрый: каждый портал-кандидат
пробивается **одним
OAuth-обновлением токена** — именно оно даёт чистый ответ `NOT_INSTALLED`.

**Важное операционное следствие:** у живого портала Битрикс при такой пробе ротирует токен, и
новый обязан быть сохранён — **это происходит и в `--dry-run`**. То есть «сухой» прогон не пишет
удалений, но токены живых порталов обновляет; безопасно, однако не считайте его прогоном без
побочных эффектов.

Опции:

- `--limit=200` — сколько порталов-кандидатов проверить за запуск.
- `--threshold=1` — минимальный `error_update` для попадания в кандидаты.
- `--expired-days=30` — через сколько дней после последнего успешного продления удалять портал с
  истёкшей подпиской. Порог строгий: ровно на границе портал остаётся.
- `--dry-run` — показать, что было бы удалено (с оговоркой про ротацию токенов выше).

Срок подписки считается по `b24_apps.expires`: оно обновляется только при успешном продлении
токена и у портала с кончившейся подпиской замирает на дате последнего удачного обновления.
Отдельной колонки под дату отказа нет намеренно — миграция для этой команды не нужна.

Каждое удаление пишется в лог: `info` `removed dead portal` с `member_id`, `domain`, `reason` и
`expires`.
