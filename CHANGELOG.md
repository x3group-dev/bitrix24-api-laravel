версии — по [семантическому версионированию](https://semver.org/lang/ru/).

## [3.4.3] — не выпущено

### Исправлено

- **Переименование портала больше не отправляет запрос в бесконечный цикл.** Когда портал
  переименован, Битрикс отвечает на каждый REST-вызов редиректом `302` на новый адрес.
  `Core::call()` это обрабатывает: читает новый домен, зовёт `Credentials::changeDomainUrl()`
  и рекурсивно повторяет вызов. Но SDK-шный `changeDomainUrl()` делает
  `$this->endpoints->changeClientUrl($domainUrl);` и **выбрасывает результат**, а
  `Endpoints::$clientUrl` объявлен `readonly` — то есть `changeClientUrl()` не мутирует
  объект, а возвращает новый. Домен не меняется, повтор уходит на тот же старый адрес,
  снова прилетает 302 — и так до бесконечности.

  Потолок `max_duration` из 3.4.2 тут бессилен: он ограничивает длительность одного вызова,
  а бесконечен запрос, состоящий из быстрых (~100 мс) вызовов. Так 2026-09-01 лёг прод
  приложения dependent-fields — воркеры php-fpm сидели в этой рекурсии часами (сигнатура:
  ровно одна побудка в секунду и растущий от стека RSS), пул исчерпался, nginx сутки отдавал
  502. У одного переименованного портала за сутки набралось 39 363 повтора, то есть ни
  одного полезного вызова.

  Починено наследником `X3Group\Bitrix24\Core\B24Credentials`, у которого смена домена
  действительно применяется; `B24ServiceBuilderFactory::init()` теперь строит именно его.
  Дальше всё работает само: повтор уходит на новый домен и отправляется
  `PortalDomainUrlChangedEvent`, по которому `PortalDomainUrlChangedListener` пишет новый
  домен в базу — портал лечится сам, без ручной правки.

  Дефект присутствует и в свежем `bitrix24/b24phpsdk` 3.5.0, поэтому апгрейд SDK его не
  закрывает. Канареечный тест `vendor_credentials_still_ignore_domain_change` покраснеет,
  когда это починят апстримом, — тогда наследника можно будет убрать.

## [3.4.2] — не выпущено

### Исправлено

- **У исходящих REST-запросов появился жёсткий потолок длительности.** У Symfony HttpClient
  опция `timeout` — это таймаут ПРОСТОЯ (сколько ждать очередную порцию данных), а не общее
  время запроса; общее ограничивает только `max_duration`, и по умолчанию она равна нулю,
  то есть «без ограничения». Потолка не ставил никто: обёртка создавала клиент голым
  `HttpClient::create()`, а SDK-шный `CoreBuilder` задаёт лишь `'timeout' => 120`. Поэтому
  портал, который принял соединение и отвечает по капле, держал php-fpm воркер сколько
  угодно: idle-таймаут не срабатывает, потому что данные идут, `max_execution_time` не
  считает время в I/O, а `request_terminate_timeout` в пуле обычно не задан. В приложении
  dependent-fields это положило прод на сутки — 18 из 20 воркеров сидели по 2–5 часов в
  одном вызове, пул исчерпался, nginx отдал 84 128 ответов 502.

  Теперь клиент рождается в `X3Group\Bitrix24\Core\B24HttpClientFactory` с
  `max_duration = 120` и `timeout = 60` (настраиваются через `config('bitrix24.http.*')`
  и переменные `BITRIX24_HTTP_MAX_DURATION` / `BITRIX24_HTTP_TIMEOUT`; ноль и отрицательные
  значения игнорируются — это и есть «без ограничения»). Все обычные REST-вызовы идут через
  `X3Group\Bitrix24\Core\B24ServiceBuilderFactory` — замену SDK-шной `ServiceBuilderFactory`,
  которая собирает ядро с этим клиентом.

- **Биндинг `Bitrix24\SDK\Core\ApiClient` перестал падать при резолве.** В b24phpsdk 3.x у
  конструктора шесть аргументов, а передавалось пять: без `$urlFormatter` любой
  `app()->make(ApiClient::class, ...)` бросал `ArgumentCountError`.

## [3.4.1] — не выпущено

### Исправлено

- **`B24AuthUserMiddleware` больше не отвечает 500 на запрос без `X-b24api-expires-in`.**
  Заголовок обязателен наравне с `member-id`, `domain` и `access-token` — он уходит в
  `AuthToken::$expires`, объявленный как non-nullable `int`, — но единственный из четырёх
  не проверялся. Без него конструктор бросал `TypeError`, и запрос падал пятисоткой вместо
  осмысленного отказа. Теперь отдаётся 406 `X-b24api-expires-in is null`, а для нечислового
  значения — `X-b24api-expires-in is not an integer`. Тексты трёх прежних отказов не менялись.
- **Любой `\Error` внутри блока авторизации становится 401, а не 500.** Прежний
  `catch (\Exception)` не перехватывал `\Error`, поэтому мимо него проходил и упомянутый
  `TypeError`, и любой будущий дефект того же рода. Наружу отдаётся 401 без деталей
  (`authorization failed`): в сообщении `Error` лежат пути `vendor`. Подробности пишутся
  в лог вместе с `member_id`.

## [3.4.0] — не выпущено

### Добавлено

- Колонка `b24_apps.user_id` — явный владелец app-токена портала. `NULL` означает «владелец
  не установлен или не доверен»: правило 2 для такой строки не срабатывает.
- Команда `bitrix24:backfill-app-owner` — проставляет владельцев порталам, установленным до
  появления колонки. Идемпотентна, повторный запуск — штатный режим.
- Команда `bitrix24:reanchor-app-token` — ремонт порталов, у которых app-токен принадлежит не
  администратору.
- Исключение `InstallerCannotOwnPortalException` с полями `memberId` и `userId`.

См. [`docs/console-commands.md`](docs/console-commands.md).

### Изменено

- **Ломающее: установка не-администратором теперь падает.** Раньше первую установку портала мог
  выполнить кто угодно. Теперь профиль проверяется на обоих путях установки, и если ставящий не
  администратор либо пришёл без `ID`, установка прерывается `InstallerCannotOwnPortalException` и
  не пишется ничего — ни токен, ни владелец, ни строка портала.

  Ловите исключение в install-контроллере, чтобы показать «поставить приложение может только
  администратор». Бросается оно **до** `AppSetupRunner`, поэтому не-админский `ONAPPINSTALL`
  больше не прогоняет установщиков: переустановку теперь обязан делать администратор.

- Запись в `b24_apps` ограничена двумя правилами: установка или переустановка администратором, и
  перенос обновлённого токена из `b24_users`, если этот пользователь и есть владелец портала.
  Токен любого другого сотрудника в строку портала больше не попадает.

### Порядок обновления

**`migrate` обязан оказаться на сервере раньше нового кода или вместе с ним.** В окне, где новый
код работает на старой схеме, `AppTokenWriter::saveIfAllowed()` падает с `no such column: user_id`
уже **после** записи токена: портал получает токен, но остаётся без полей и обработчиков событий.

Миграция только заводит колонку — заполнение и ремонт вынесены в команды:

```bash
php artisan migrate                                # только колонка user_id
php artisan bitrix24:backfill-app-owner --dry-run  # что заполнится
php artisan bitrix24:backfill-app-owner            # проставить владельцев
php artisan bitrix24:reanchor-app-token --dry-run  # план ремонта оставшихся
php artisan bitrix24:reanchor-app-token            # починить
```

## [3.3.1] — 2026-07-28

### Исправлено

- `EventDispatcherAdapter` держит слушателей в приватном диспетчере экземпляра, а не на глобальном
  диспетчере Laravel. Раньше слушатель «сохранить обновлённый токен в `b24_apps`» срабатывал на
  обновление **любого** токена, включая пользовательский, и токен рядового сотрудника затирал
  app-токен портала — после чего админ-методы Битрикс24 отвечали «нет прав».
- Объявлена зависимость `illuminate/events`: она использовалась в `src/`, но приезжала транзитивно.

**Поведенческое изменение:** `listen()` больше не регистрирует слушателя глобально. Слушателей
уровня приложения вешайте через `Event::listen`.
