Пакет Laravel для удобной работы с REST API Битрикс24 и написания приложений.

Включает в себя:
- Миграции для сбора статистики запросов и сохранения авторизации(токенов) пользователей
- Роуты в зависимости от типа приложения и запросов к нему
- Шаблоны для установки и работы приложения
- Проверку статуса порталов на которые было установлено приложение
- Автоматическое обновление токенов пользователей

Установка

```injectablephp
composer require x3group-dev/bitrix24-api-laravel
```

Выполнить публикацию (скопируются routes, blade, базовые контроллеры)
```injectablephp
php artisan vendor:publish --provider="X3Group\Bitrix24\Bitrix24ServiceProvider"
```

Выполнить миграции
```injectablephp
php artisan migrate
```

В адреса приложений вписываем

Приложение:
```injectablephp
https://host/app
```
Установка приложения:
```injectablephp
https://host/install
```

в файл .env добавляем и заполняем своими данными
```injectablephp
BITRIX24_PHP_SDK_APPLICATION_CLIENT_ID=
BITRIX24_PHP_SDK_APPLICATION_CLIENT_SECRET=
# вместо crm,user_brief укажите скоупы приложения
BITRIX24_PHP_SDK_APPLICATION_SCOPE="crm,user_brief"
BITRIX24_LOG_MAX_FILES=3
```

В сборку фронта добавить проброс авторизации в заголовках, чтобы работали роуты b24appFrontRequest

```injectablephp
BX24.ready(async function () {
    await BX24.init(async function () {
        window.axios.defaults.headers.common['X-b24api-access-token'] = BX24.getAuth().access_token;
        window.axios.defaults.headers.common['X-b24api-refresh-token'] = BX24.getAuth().refresh_token;
        window.axios.defaults.headers.common['X-b24api-domain'] = BX24.getAuth().domain;
        window.axios.defaults.headers.common['X-b24api-member-id'] = BX24.getAuth().member_id;
        window.axios.defaults.headers.common['X-b24api-expires-in'] = BX24.getAuth().expires_in;
    });
});
```

**Cron**

Для автообновления токенов приложения обязательно требуется добавить запись в crontab

```php
* * * * * cd /path-to-your-project && php artisan schedule:run >> /dev/null 2>&1
```

## Миграция на b24phpsdk ^3 (SDK 3)

Начиная с версии 3.0.0 пакет переведён на официальный `bitrix24/b24phpsdk ^3` и требует **PHP 8.4**. В SDK 3 адрес OAuth-сервера (обновление токенов) задаётся через объект `Endpoints` и хранится отдельно для каждого портала.

- Требуется **PHP 8.4** и `bitrix24/b24phpsdk ^3`.
- В таблице `b24_apps` добавлена колонка `oauth_server_url` (миграция включена) — адрес OAuth-сервера (v3 `Endpoints`), используемый для обновления токенов. Значение выводится автоматически из `SERVER_ENDPOINT` запроса установки/плейсмента; фолбэк — EAST `https://oauth.bitrix24.tech/` (захардкожен в `OauthServerUrlResolver`, переменная окружения не нужна).
- В таблице `b24_users` отдельной колонки нет — адрес OAuth-сервера резолвится из `b24_apps` по `member_id`.
- Потребителям при обновлении необходимо перейти на **PHP 8.4** и выполнить `php artisan migrate`.

## Установщики приложения (реестр, с 3.1.0)

Создание сущностей приложения (списки, entity, встройки, поля и т.п.) при установке вынесено в **реестр
установщиков** — приложению больше не нужен свой install-контроллер, только классы-установщики.

- Класс реализует интерфейс `X3Group\Bitrix24\Contracts\Bitrix24Installer`:
  ```php
  public function install(\Bitrix24\SDK\Services\ServiceBuilder $b24): void;
  ```
- Регистрируются упорядоченным списком в `config('bitrix24.installers')`:
  ```php
  'installers' => [
      App\Install\InstallEvents::class,
      App\Install\InstallLists::class,
      // ...в нужном порядке
  ],
  ```
- **Когда это выполняется.** Весь install-флоу (`InstallService`: запись app-токена + прогон
  установщиков) работает **только на установке/переустановке приложения** — это маршрут **`/install`**
  (`InstallController`) и серверное событие **`ONAPPINSTALL`** (`OnApplicationInstallController`). На
  обычных открытиях приложения (главный маршрут `/app`, плейсменты, front-запросы) install-флоу **НЕ
  запускается** и app-токен не трогается — там работает пер-юзерная авторизация (`b24_users` через
  middleware). Установщики вызываются **по порядку**, из одного места (идемпотентно).
- **Установщики ОБЯЗАНЫ быть идемпотентны.** Ошибка любого установщика логируется и пробрасывается
  (fail-loud), страница установки показывает `install-fail` — то есть неидемпотентный установщик (напр.
  «поле уже существует») превратит **повторную установку/переустановку** в экран ошибки.
- **App-токен портала** (`b24_apps`) — пишется **только на установке/переустановке** (`/install` /
  `ONAPPINSTALL`) и только если устанавливающий — **администратор** (`profile->ADMIN`). Проверка
  идёт на **обоих** путях и **не сокращается для первой установки портала**: владельцем портала
  (`b24_apps.user_id`) записывается тот, кто установил приложение, и не-админ во владельцах —
  это портал с не-админским app-токеном, на котором админ-методы (`userfieldconfig.*`) падают
  «нет прав».
- **Установка не-админом — жёсткая ошибка.** Профиль устанавливающего запрашивается на обоих
  путях, и если он не админ (либо пришёл без `ID`, то есть владельца записать нечем), установка
  прерывается исключением `InstallerCannotOwnPortalException` и **не пишется ничего** — ни токен,
  ни владелец, ни строка портала. Потребителю имеет смысл ловить его отдельно, чтобы показать
  «поставить приложение может только администратор» вместо общего экрана ошибки.
- Любая запись в `b24_apps` — и на установке, и при обновлении токена — проходит через
  `AppTokenWriter`: токен не-админа существующую строку не перезатирает, а обновлённый токен
  уезжает в `b24_apps` только от владельца портала. Правила и то, как чинить уже пострадавшие
  порталы, — в разделе «Владелец app-токена портала» ниже.
  По умолчанию `installers` пуст — обратная совместимость.

## Владелец app-токена портала (`b24_apps.user_id`)

В `b24_apps` есть колонка `user_id` — **владелец** app-токена портала, то есть пользователь
Битрикс24, чьим токеном приложение ходит в REST от имени всего портала. Владелец
**записывается один раз, при установке приложения**, и обновлением токена больше не меняется.

`user_id = NULL` означает «владелец не установлен или не доверен». Для такой строки правило 2
(ниже) не срабатывает вовсе — поведение fail-closed: лучше не обновлять токен портала совсем,
чем обновить его чьим попало.

Зачем колонка: до неё владение было неявным — оно закодировано только внутри самой строки
токена, поэтому любая запись молча меняла владельца. Так токен рядового сотрудника оказывался
в `b24_apps`, после чего админ-методы (`userfieldconfig.*`) начинали падать «нет прав», а
понять, чей токен лежит в строке, можно было только декодированием токена.

### Два правила записи в `b24_apps`

**Правило 1 — установка и переустановка.** Маршрут `/install` и событие `ONAPPINSTALL`.
Пишет токен и владельца, и только если устанавливающий — администратор (см. раздел выше).

**Правило 2 — обновлённый токен владельца.** Свежий токен пользователя из `b24_users`
переносится в `b24_apps` только тогда, когда этот пользователь и есть записанный владелец
портала. Токен любого другого сотрудника в `b24_apps` не попадает.

Срабатывает правило 2 в двух местах, и основное из них — не хранилище:

- **`B24AppUserMiddleware` — владелец открыл приложение** (обычный заход на размещение). На
  практике это основной путь, которым app-токен портала остаётся живым: владелец приходит сюда
  на каждом открытии приложения.
- **`UserAuthDatabaseStorage::saveRenewedToken()`** — токен протух прямо посреди запроса и был
  обновлён по OAuth. Путь редкий, срабатывает по случаю.

Правило 2 меняет ровно четыре колонки — `access_token`, `refresh_token`, `expires`,
`expires_in` — и сбрасывает `error_update`. Владельца, `domain`, `application_token` и
`oauth_server_url` не трогает: владелец меняется исключительно установкой. Если строки
`b24_apps` для портала ещё нет, не делает ничего.

### Обновление с версии ниже 3.4.0

**Ломающее изменение поведения: установка не-администратором теперь падает.** Раньше самую
первую установку портала мог выполнить кто угодно — `shouldWrite(appExists: false, …)`
пропускал её без проверки прав. Теперь профиль устанавливающего запрашивается на **обоих**
путях (`/install` и `ONAPPINSTALL`), и если он не админ — либо пришёл без `ID`, то есть
владельца записать нечем, — установка прерывается исключением
`InstallerCannotOwnPortalException` и **не пишется ничего**: ни токен, ни владелец, ни строка
портала. Ловите его отдельно в своём install-контроллере и показывайте «поставить приложение
может только администратор» вместо общего экрана ошибки; `member_id` и `user_id` доступны
одноимёнными полями исключения.

**Следствие, которое легко пропустить: переустановка не-админом больше не переустанавливает
приложение.** Исключение бросается ДО `AppSetupRunner`, поэтому не-админский `ONAPPINSTALL`
теперь не выполняет установщиков вовсе — поля, обработчики событий и прочие идемпотентные
шаги не перерегистрируются. Раньше он их выполнял (пропускалась только запись токена), и
рядовой сотрудник, переустановивший приложение, чинил этим потерянные поля. Теперь такую
переустановку обязан делать администратор.

**Миграция.** `php artisan migrate` добавляет колонку и заполняет её для уже установленных
порталов: владелец декодируется из самого `access_token` и принимается, **только если это
подтверждённый администратор** по `b24_users`; иначе строка остаётся с `NULL`, чтобы не
узаконить уже подменённого владельца. Миграция печатает сводку (сколько заполнено, сколько
осталось `NULL` и почему) и список порталов на ремонт — этот список и есть вход для
`bitrix24:reanchor-app-token`. Миграция повторно запускаема: если бэкофилл оборвётся на
середине, повторный `migrate` продолжит с места обрыва.

**Порядок выкатки. `migrate` обязан оказаться на сервере раньше нового кода или вместе с
ним — не «первым пунктом списка», а раньше по времени.** Если у вас код выкатывается одним
шагом, а `php artisan migrate` запускается следующим, между ними есть окно, в котором новый
код работает на старой схеме, и это окно ломает установки: `AppTokenWriter::saveIfAllowed()`
падает с `SQLSTATE[HY000]: no such column: user_id` **уже после того, как токен записан**.
Установка отдаёт 500 на середине, `AppSetupRunner` не запускается вовсе — то есть портал
получает токен, но не получает ни полей, ни обработчиков событий. Выкатывайте миграцию первым
шагом деплоя (или переведите деплой в режим «migrate до переключения кода»), а не после него.

Дальше: `bitrix24:reanchor-app-token --dry-run` (посмотреть план) → боевой прогон ремонта.

### Что искать в логах

- **`notice` — единственный громкий сигнал.**
  `b24 app token: propagation blocked (refresh by non-owner)` — токен портала пытался
  обновить не его владелец, перенос заблокирован. На здоровом флоте таких записей должно быть
  около нуля, и каждая — либо попытка подмены app-токена, либо протухший `user_id`, из-за
  которого блокируется законный рефреш. Ровно этого сигнала не хватало во время инцидента: о
  поломке узнавали от клиента. (Есть и второй notice — `b24 app token: keep existing
  (non-admin overwrite blocked)` из `AppTokenWriter::saveIfAllowed()`; внутри пакета установка
  до него больше не доходит, раньше сработает гейт админства, но метод публичный.)
- **`debug` — штатные пропуски.** Тихие намеренно: на флоте в тысячи порталов на уровне notice
  они превратились бы не в строчку лога, а в сам лог.
  - `propagation skipped (portal owner not established)` — у портала `user_id IS NULL`.
    Считать такие порталы всё равно удобнее одним запросом
    `select count(*) from b24_apps where user_id is null`, чем по логу.
  - `propagation skipped (placement user not identified)` — профиль пришёл без `ID`. Сегодня
    эта ветка недостижима (`b24_users.user_id` объявлен `NOT NULL`, такой запрос падает
    раньше) — искать её в логе бесполезно, она стоит на случай ослабления колонки.
  - `propagation skipped (placement carries no refresh token)` — размещение пришло с пустым
    `REFRESH_ID`, переносить нечего.
- `info` — нормальный ход дел: `b24 app token: saved` (установка) и
  `b24 app token: propagated from owner` (сработало правило 2).

Во всех событиях владелец лежит в контексте под ключом **`owner_user_id`**, а тот, кто
пришёл с токеном, — под `user_id`. Слово «owner», а не «installer», выбрано намеренно: после
прогона `bitrix24:reanchor-app-token` новый владелец приложение не устанавливал, так что
«installer» был бы неправдой.

### Ремонт: `bitrix24:reanchor-app-token`

```bash
php artisan bitrix24:reanchor-app-token --dry-run
php artisan bitrix24:reanchor-app-token
```

Чинит порталы, у которых app-токен принадлежит не администратору: подбирает администратора
портала по `b24_users` и перепривязывает портал на него.

**Перепривязка пишет и токен, а не только колонку** — и это принципиально. Сама по себе смена
`user_id` не чинит ничего: правило 2 донесёт до `b24_apps` свежий токен нового владельца лишь
тогда, когда тот сам откроет приложение. Администратор, который во фронтенд приложения не
заходит, не сделает этого никогда, и портал остался бы со сломанным токеном навсегда, а в
колонке значилось бы, что он починен. Поэтому команда переносит токен админа целиком и
обнуляет `error_update` (при `error_update >= 10` портал выпадает из ротации обновления
токенов). Результат проверяется живым вызовом `user.admin`, и у него **три** исхода, а не два:

- **перепривязан** — проверка сказала «админ», запись остаётся;
- **откат** — проверка не прошла (или портал недоступен), и строка возвращается к прежним
  значениям целиком, все шесть колонок;
- **откат отменён** — проверка не прошла, но за время проверки строку успел переписать
  кто-то ещё (живой вызов идёт по шине `appEvents`, слушатель которой сохраняет обновлённый
  токен прямо в `b24_apps`). Слепой откат вернул бы туда значение, которое Битрикс уже
  отозвал, то есть добил бы портал; поэтому токен оставляется чужой, свежий, а **владелец
  возвращается прежний** — оставить в `user_id` подтверждённого не-админа значило бы
  застабилизировать исходную аварию инструментом ремонта.

Все три исхода видны в сводке отдельными счётчиками. Прогон, в котором не выжила ни одна
перепривязка, возвращает ненулевой код.

Порталы раскладываются по пяти корзинам:

| корзина | что это значит | что делать |
| --- | --- | --- |
| **здоров** | владелец записан и подтверждён админом в `b24_users` | ничего, портал не трогается |
| **на ремонт** | владельца нет либо про него точно известно, что он не админ, — и на портале есть админ со свежим токеном | команда чинит сама; только эта корзина расходует `--limit` (счётчики остальных — всегда полные) |
| **ждёт входа админа** | админы на портале есть, но у всех токен старше `--max-age` | достаточно, чтобы **любой администратор один раз открыл приложение**: `B24AppUserMiddleware` обновит его строку в `b24_users`, и следующий прогон портал починит. Переустановка тут ни при чём |
| **нужна переустановка** | про владельца точно известно, что он не админ, а перепривязаться не на кого | настоящая поломка, которую сами мы не чиним: нужна переустановка приложения администратором |
| **нет данных** | свидетельств о правах владельца нет вовсе. Это **два** случая: либо владелец записан, но строки о нём в `b24_users` нет, либо владельца нет (`user_id IS NULL`) и админов на портале тоже нет | ничего; **это не «нужна переустановка»**, см. ниже |

**«Нет данных» — не поломка.** `b24_users.is_admin` заполняет только `B24AppUserMiddleware`,
то есть заход пользователя на фронтенд приложения. Приложение, живущее на одной API-группе
роутов (`routes/b24app.php`), `b24_users` не заполняет вообще — у него в «нет данных»
закономерно попадает весь флот, хотя каждый его портал установлен администратором, прошедшим
живую проверку при установке. Подтвердить владельца по базе там просто нечем, и звать клиентов
на переустановку не за что.

Именно у такого приложения работает **вторая** ветка корзины — `user_id IS NULL` и ни одного
админа в `b24_users`, — и она же там доминирует: после бэкофилла порталы делятся на «владельца
не подтвердили, остался `NULL`» и «`user_id` заполнен со старой установки», и обе разновидности
попадают в «нет данных» разными ветками. Поэтому корзина описана двумя случаями, а не одним:
считать «нет данных» только про заполненный `user_id` значило бы отправить весь флот
API-приложения в «нужна переустановка».

Опции:

- `--dry-run` — показать план, не записывая ничего.
- `--member=` — обработать только этот `member_id`.
- `--user=` — взять токен именно этого пользователя портала; он обязан быть администратором,
  иначе гейт откажет. Действует **только на порталы из корзины ремонта**; остальные корзины
  как показывались, так и показываются.
- `--limit=200` — максимум **ремонтируемых** порталов за прогон, `0` — без ограничения.
  Бюджет расходует только корзина ремонта, поэтому непочиняемые порталы его не съедают.
  **Счётчики в сводке при этом всегда полные, за весь флот** — диагностические корзины не
  делают ни одного REST-вызова и ничего не пишут, ограничивать их нечего. Обрезаются только
  строки таблицы, и, если что-то скрыто, команда говорит об этом отдельной строкой
  («в таблице показаны не все»). Так «на переустановку: N» можно читать как настоящее N, а
  не как `min(N, --limit)`.
- `--max-age=30` — не брать в новые владельцы админа, чей токен не обновлялся дольше стольких
  дней (`0` — без ограничения). Порог защищает от замены живого токена не-админа на мёртвый
  токен админа: у сломанного портала токен обычно живой, а найденный на замену админ мог не
  заходить в приложение месяцами.
- `--skip-verify` — не проверять результат живым вызовом `user.admin`. **Разрешён только
  вместе с `--member`:** без живой проверки прогон способен разложить по флоту мёртвые токены,
  а обратного прогона нет.

## Вычистка мёртвых порталов

```bash
php artisan bitrix24:remove-uninstalled --dry-run
php artisan bitrix24:remove-uninstalled
```

Удаляет токены порталов, которые уже не оживут: с которых приложение удалено
(OAuth `NOT_INSTALLED`) и у которых подписка кончилась больше `--expired-days`
назад (OAuth `PAYMENT_REQUIRED`, по умолчанию 30 дней). Сетевые ошибки и таймауты
не трогает.

- Опции: `--limit=200`, `--threshold=1`, `--expired-days=30`, `--dry-run`.
- Срок подписки считается по `b24_apps.expires` — оно обновляется только при успешном
  продлении токена, поэтому миграция не требуется.
- Каждый портал пробивается одним OAuth-обновлением токена. У живого портала Битрикс
  при этом ротирует токен, и новый сохраняется — это происходит и в `--dry-run`.

## Структурированное логирование

Пакет умеет собирать структурированный JSON-лог REST-вызовов Битрикс24 и ошибок
приложения — для последующей централизованной доставки (Vector → ClickHouse) и разбора.
**По умолчанию выключено: пока не включишь — поведение пакета не меняется вовсе, ничего
не пишется.** Подключение zero-config: пакет уже установлен, канал регистрируется через
auto-discovery, включается парой переменных `.env`.

**Как включить**

```injectablephp
STRUCTURED_LOG_ENABLED=true
APP_LOG_NAME=base
# необязательные:
STRUCTURED_LOG_PATH=storage/logs/structured/app.json
STRUCTURED_LOG_MAX_FILES=14
STRUCTURED_LOG_TRUNCATE_AT=200
```

- `APP_LOG_NAME` — метка `app` в каждой записи (какое приложение пишет); если пуст,
  берётся `config('app.name')`. Задавайте явно, когда логи многих приложений сливаются
  в одно хранилище.

**Что пишется**

- **REST-вызовы Битрикс24** — ровно одна запись на вызов: метод, параметры (для
  воспроизведения) и исход (`ok`/`http`/`duration_ms`, `id` либо `count`, при ошибке —
  `error`). Полный `result` не тащится. Многословный debug-поток родного SDK в этот
  канал не течёт.
- **Ошибки приложения** — записи уровня `WARNING` и выше (`Log::warning/error`,
  необработанные исключения) дублируются в тот же файл. Стек логирования приложения при
  этом не переопределяется — канал работает как дополнительный приёмник.

**Где файл и ротация**

`storage/logs/structured/app.json` через monolog `RotatingFileHandler` (daily) — реально
пишется `app-ГГГГ-ММ-ДД.json`, старые файлы monolog удаляет сам, оставляя последние
`STRUCTURED_LOG_MAX_FILES` дней. Локальный файл — это короткий буфер на случай
недоступности доставки, а не архив; долгое хранение — в ClickHouse по TTL (см. ниже).

**Что маскируется**

- **Секреты** — значения ключей `auth`/`AUTH`, `access_token`, `refresh_token`,
  `application_token`, `webhook_token` и JWT-подобные строки (`eyJ…`) → `***`,
  рекурсивно по всей записи.
- **Персональные данные** — только для методов `user.*` вырезаются `NAME`, `LAST_NAME`,
  `SECOND_NAME`, `EMAIL`, `PERSONAL_MOBILE`, `PERSONAL_PHONE`, `WORK_PHONE`, `LOGIN`.
  Вне `user.*` не трогаются (чтобы, например, `NAME` заголовка статьи сохранился).
- **Длинный контент** — любая строка длиннее `STRUCTURED_LOG_TRUNCATE_AT` (дефолт 200)
  обрезается с пометкой полной длины: `«…первые 200 символов… (всего N символов)»`.

Списки ключей-масок и лимит обрезки настраиваются в `config/structured-logging.php`
(`php artisan vendor:publish --provider="X3Group\Bitrix24\Bitrix24ServiceProvider"` для
переопределения; работает и с дефолтами без публикации).

**Поле `schema_version`**

Каждая запись помечена `schema_version` (старт `"1"`) — константой формата в коде пакета.
При несовместимом изменении состава полей версия поднимается, чтобы хранилище и разбор
различали старые и новые записи и не ломались на них.

Доставка лога в хранилище (Vector → ClickHouse) — задача инфраструктуры, от кода
приложения не зависит; чек-лист девопсу: [`docs/structured-logging-infra.md`](docs/structured-logging-infra.md).
